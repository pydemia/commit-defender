## C07 통합 구현 checkpoint

작업 경로는 `/Users/a09255/git/commit-defender-preventive-review`, branch는 `feat/preventive-review-platform`, 기준 commit은 `35575ad`다. 기존 원본 checkout `/Users/a09255/git/commit-defender`의 `AGENTS.md`와 phoenix submodule 변경은 보존했다. 이번 확인에서 두 내용의 SHA-256은 이전 기록과 동일했다.

수동 리뷰는 `createReviewBackend`에서 GCR standalone worker로 들어간다. `standaloneReview.ts`가 index/working-tree snapshot, profile·worktree의 암호화 Memory/Skill, context/policy, Codex account executor를 연결한다. 준비한 factory 객체는 worker 안에서 유지하고 종료 report를 공통 contract로 projection한다. 실패·취소를 포함한 admitted report는 암호화 history에 저장한다. 저장 확인에 실패하면 결과를 보존하고 별도 진단을 출력한다. Repository 설정이나 Skill이 실행 권한을 부여할 수 없으며 지원하지 않는 선택에는 provider fallback이 없다.

`ReviewExecutionOwner.prepare`는 비동기 캡처 후 실제 source/context identity로 진행 중인 실행과 중복 여부를 확인한다. 같은 실행의 중복 준비는 worker를 해제한다. 다른 준비가 도착하거나 clear/cancel하면 이전 준비에 취소를 전달하고 늦게 준비된 snapshot을 실행하지 않는다. 기존 실행은 새 준비가 유효한 job을 반환할 때까지 결과 소유권을 유지한다. Worker의 종료 확인 후 실행 promise를 완료하며 extension deactivate는 남은 정리를 기다린다. 준비 단계의 진행 표시와 취소도 연결했다.

사용자 설정의 provider·모델·실행 경로·profile만 standalone 실행에 사용한다. 저장소에만 있는 기존 account 설정은 보존하되 재사용하지 않는다. 기존 account 선택 UI는 User Settings에 저장하며 Codex의 현재 지원 조합 `gpt-6-astra` / `xhigh`를 제시한다. 새 설치의 stage 자동 실행은 꺼져 있고 repository 설정으로 켤 수 없다. 기존 commit-message adapter와 legacy hook은 별도 경로를 유지한다. Hook의 credential 처리는 C08에서 변경한다.

Local Memory and Skills 화면은 profile/worktree 선택, candidate 생성, 편집, 활성화·비활성화·archive·삭제, 명시적인 plaintext export, hash를 검증하는 import를 제공한다. 본문은 CSP가 적용된 textarea에서 편집하며 VS Code 임시 문서나 repository 파일로 자동 저장하지 않는다. 변경에는 core의 revision 검사를 적용한다. 선택한 profile의 encrypted history를 재시작 후 읽을 수 있도록 연결했고 CLI의 다른 프로세스에서 생성한 이력도 명시적으로 refresh할 수 있다. 저장된 working-tree review의 재분석은 기록된 파일 선택을 유지한다.

Summary는 immutable GCR report와 별도로 현재 local entry의 revision·state·expiry를 확인한다. 이 관찰은 사용했던 entry의 최신성 검사다. 새로 추가된 항목까지 포함한 전체 context 재계산을 의미하지 않는다. Source/context hash, criteria revision, source-read provenance·range·hash, anchor 검증과 evidence/counter-evidence 평가를 표시한다. Standalone summary/status bar에는 advisory를 표시하며 grade를 만들어 넣지 않는다.

## C08 source checkpoint — 모델 credential과 hook migration

모델 API credential을 개인 지식과 분리했다. OS service는 `com.commitdefender.model-credentials.v1`, application-data 하위 경로는 `model-credentials/v1`이다. GCR alpha.9의 OS wrapping-key adapter와 AES-256-GCM record store를 사용하며 personal Memory/Skill의 key reference와 저장 디렉터리를 재사용하지 않는다. Store를 닫고 OS key와 record를 다시 열어 확인한 뒤 참조를 반환한다.

참조는 profile·provider·endpoint·model/deployment·Azure API version에 묶인다. API endpoint는 HTTPS와 loopback HTTP만 허용하고 API 요청의 redirect를 금지했다. Provider가 오류 본문에 key를 직접 또는 URL encoding으로 되돌려도 해당 값은 진단에서 제거한다. Credential 값은 repo 설정·환경 변수로 실행 경로를 선택하는 데 사용하지 않는다.

`Manage Model API Credential` 명령으로 password 입력, 기존 저장 key 선택, 명시적 교체, User/Workspace Settings 또는 hook의 기존 평문 migration을 제공한다. Settings와 새 hook JSON에는 참조만 쓴다. `getConfig()`와 headless runtime은 기존 `apiKey`를 fallback으로 읽지 않는다. 기존 source와 선택한 destination을 재확인하고 암호화 key와 settings reference의 read-back이 끝난 뒤 선택한 평문만 제거한다. 다른 저장 값과 충돌하면 migration은 기존 값을 보존한다. Key 교체는 별도 확인과 expected revision이 필요하다.

Hook의 일반 설정 반영은 legacy plaintext를 덮지 않는다. 명시적 migration은 bounded regular-file read, 원본 bytes 확인, cooperating-process lock과 atomic 0600 replacement로 처리한다. 저장 뒤 중단된 migration은 공개 destination identity를 이용해 재개할 수 있고 새 평문 journal을 만들지 않는다. 종료된 writer의 lock은 복구하지만 살아 있는 writer의 lock은 보존한다. VS Code settings adapter는 변경 전 값을 재확인하며 여러 VS Code process/files에 대한 atomic transaction을 제공하지는 않는다.

Commit-message generation과 hook은 같은 resolver를 사용한다. Credential 준비도 execution owner가 추적하므로 profile 변경이나 extension 종료 뒤 늦게 model 실행을 시작하지 않는다. Codex 등 account CLI의 기존 로그인 자료는 그대로 사용하고 복사·이전하지 않는다. Hook script의 기존 signature와 legacy P3 판정은 유지했으며 공통 core의 trigger 연결은 P07에 남아 있다.

### 검증과 artifact

[source-checkpoint](evidence/P02-C08-source-checkpoint.json)에 검증 범위와 미완료 항목을 기록했다.

- 전체 `npm test` 123개 통과. 명시적 key 교체와 revision 검사를 추가한 뒤 credential suite 13개를 Node 25.9.0과 18.20.8에서 통과했다. 앞서 Node 18에서 provider/config/credential 25개도 통과했다. 최종 `typecheck:test`, build, diff check가 통과했다.

- [macOS 첫 검사](evidence/P02-C08-credential-macos.json)는 credential migration 뒤 VS Code 임시 socket path 길이 제한으로 시작에 실패했다. 생성한 OS key와 profile은 제거했다. 짧은 임시 경로로 수정한 [VS Code 1.135.0 검사](evidence/P02-C08-credential-macos-attempt2.json)와 [VS Code 1.90.2 검사](evidence/P02-C08-credential-macos-minimum.json)가 통과했다.
- 실제 Keychain과 기본 application-data 경로에 합성 key를 저장했다. 실제 Extension Host가 plaintext 없는 User Settings의 참조로 commit message를 만들었고 Host가 종료된 뒤 독립적으로 복사한 단일 hook bundle도 같은 key로 요청했다. 두 검사에서 localhost 합성 API 요청은 총 4회이고 실제 모델 호출은 0회다. 검증에는 새 합성 key만 제공했고 사용자의 기존 model credential은 migration하지 않았다.
- Endpoint 변경은 request 전에 거부했다. 생성한 OS key를 삭제한 뒤 hook을 재실행했을 때도 다른 key나 평문으로 fallback하지 않았으며 config를 보존했다. 테스트 profile·OS key·임시 repo와 User Settings는 모두 정리했다. 빈 personal-knowledge profile은 생성되지 않았다.
- [최종 개발 VSIX](evidence/P02-C08-vsix-contents.json) SHA-256은 `43549161627348aa073d949d4c034748ed2021e39678d3a7748b2dd673c12c2a`다. 세 bundle은 빌드 출력과 동일하며 hook은 최소 VS Code 검증 뒤 실행한 bundle hash와 일치한다. Runtime 외부 의존성은 Node built-in과 extension의 `vscode`뿐이다. Source/test/vendor/node_modules를 제외하고 GCR license와 migration 문서를 포함했다. Artifact는 GCR의 ignored `artifacts/commit-defender/P02-C08`에 hash 이름으로 보존했다.

실제 password 입력·migration dialog를 화면에서 조작한 검증은 Mac 잠금 때문에 남아 있다. C08의 Linux end-to-end 검증은 이번 macOS 결과로 대체하지 않는다. P01/C07의 실제 화면, C07 invalid-output 원인, 후속 P03–P13과 P09 release gate도 남아 있다. Marketplace의 새 version을 게시하거나 GCR server runtime을 변경하지 않았으며 이번 C08에 해당하는 PRISM-DEV rollout은 없다.

## C07 고정 진단 전달과 실제 unselected-file 재현

세 library alpha.10을 vendor/hash/lockfile로 고정하고 실패 보고서의 고정 사유를 요약 화면에 표시했다. 보고서와 암호화 이력에 같은 문제 code/message가 남으며 provider 본문은 보존하지 않는다. 메시지의 HTML은 escape한다. 관련 검사 125개와 build·test typecheck를 통과했다. 새 VSIX 내부의 세 bundle이 현재 build와 일치하고 source/test/vendor/node_modules가 빠진 것을 확인했다. 이 VSIX는 native GUI 검증·게시 전 단계다.

Node 22의 실제 production worker와 설치한 GCR CLI alpha.4로 `gpt-6-astra/xhigh`를 실행했다. Python 정상 사례는 완료됐지만 이어진 결함 사례가 `invalid-output` / `unselected-file`로 실패했다. 출력 file 목록에 선택된 path/side 밖의 항목이 있었다는 뜻이며 버려진 원문을 보관하지 않아 어느 항목인지는 알 수 없다. 두 보고서는 CLI·별도 extension process의 저장 이력과 일치했고 중앙 호출은 0이었다. 합성 fixture·OS credential 정리를 확인했다. 이전 모든 invalid-output의 원인이 같았다고 단정하지 않는다. 다음 수정에서는 선택 결과 목록과 읽을 수 있는 근거 목록을 분리해 안내하고 같은 결함 사례를 재검증한다. [전달 기록](evidence/P02-C07-output-diagnostics-delivery.json)과 [실제 실패 기록](evidence/P02-C07-worker-output-scope-failure.json)을 따른다.

## C07 출력 범위 안내 수정의 실제 재검증

GCR `0f4738d`의 alpha.11 package를 immutable vendor와 lockfile로 고정했다. Build와 변경된 전달/standalone 검사 30개가 통과했다. 앞선 alpha.10의 회귀 검사 125개는 이전 artifact의 기록으로 구분한다.
